# LifeOS 协作说明

## 当前阶段

产品内容与用户编辑入口：[LifeOS 产品结构文稿](LifeOS-产品结构文稿.md)。该文稿按页面列出原型内容，并提供用户修改区。它用于整理产品意图；具体实施范围以本文件的当前轮任务及用户最新明确要求为准，空白项不作为开发任务。

当前产品是 `index.html` 中的单文件交互原型，已有 `server/` 下的 Node.js / Express 后端，包含模型调用、知识库、技能及定时工作流代码，后端数据使用 JSON 文件保存。核心业务数据仍分散在浏览器 `localStorage`、页面内存和示例数据中；部分技能只是占位实现。正式技术架构尚未确定，随用户确认的需求逐步制定。

## 后端方案共同设计（当前工作）

状态：需求问答中，尚未形成可执行的完整开发计划。本节记录用户确认的约束；后续补齐架构、数据结构、接口、迁移、开发阶段及验收标准后，再交由开发 agent 实施。本轮只制定方案，不修改业务代码。

### 已确认的产品边界

- 使用对象：第一版仅供用户本人使用，暂不考虑面向其他人注册的产品。
- 产品形态：以安装在个人电脑上的桌面客户端为主。
- 设备优先级：优先完成电脑端；手机端可以后续再做，不作为第一版交付的必要条件。
- 后续多设备要求：电脑和手机需要能够访问同一份个人数据，具体联网与同步方式尚未决定。
- 本地数据归属：用户明确指定本地 Obsidian 仓库（Vault）文件夹作为 LifeOS 数据的保存位置。接入方式允许 CLI 或其他本地方式；具体目录结构与接入时点待细化。
- 主要操作入口：日常使用、手动编辑和 AI 辅助修改均通过 LifeOS 前端完成。Obsidian 承担本地存储与知识留存，不要求用户直接维护文件、属性字段或 Markdown 任务格式；第一版不把完整的 Obsidian 双向业务编辑作为交付目标。
- 模型接入：用户配置自己的模型 API / API Key；支持的提供商、协议及配置粒度待确认。
- 自动化运行条件：第一版仅在电脑开机且 LifeOS 正在运行时执行定时工作流等自动化；不要求客户端退出或电脑关机后继续运行。
- 错过执行时间的处理：重新打开应用后不自动补跑，由用户通过按钮手动触发；待执行事项的展示、合并规则及防重复执行机制在详细方案中补齐。
- 后续版本方向：增加电脑关机或客户端退出后仍可持续执行自动化的能力，第一版不实施。
- 协作方式：通过逐轮问答完善方案，以本 README 作为交给其他 agent 的最终开发交接文档。

### 已确认的首版范围：西班牙语备考样板

- 用户已认可“先建立通用基础，再跑通一个完整学习场景，之后扩展其他领域”的路线；首个场景确定为西班牙语备考。
- 首版交付重点：本地 Vault 保存、通用目标/项目/任务/日历、模型与角色配置、资料和 Skill 的按需分配、AI 提案确认、学习记录、摘要自动积累与长期记忆检索，组合成可以持续使用的学习流程。
- 首个角色为“西班牙语备考老师”。角色、教材、Skill、目标等级与评估规则作为配置或领域扩展，不写死在通用任务、会话或存储服务中。
- 其他人生领域的已有页面保留；健康、财务、人脉等专属功能在后续阶段扩展。未接入功能需明确标注，不以保留界面代表功能已完成。

#### 用户的学习目标

- 学习目的：应对西班牙语考试。
- 时间范围：明年、约一年；按本轮讨论日期理解为面向 2027 年，具体起止日期及考试场次尚未确定，不自动生成固定截止日。
- 期望水平：B1–B2，用户更希望达到 B2，也接受 B1。该字段是期望目标，不代表当前已具备该水平。
- 当前水平、每周可投入时间、考试类型和所用教材尚未提供，开发示例和初始化数据均不得把它们虚构成用户事实。
- 规划建议：以 B1 作为阶段检查点，结合实际进展再推进 B2；是否采用此具体阶段划分及各阶段时长，在了解起点和投入时间后确定。不得把一年 B2 写成系统保证。

#### 对后端与学习流程的设计要求

1. 初始化时通过对话收集当前基础、目标考试、可投入时间和资料，生成可编辑的学习档案；尚未评估的能力保持未知。
2. AI 根据档案生成阶段计划，再拆成具体学习任务，关联能力维度、材料、预计用时、完成要求和原始目标；确认后保存。用户可在 LifeOS 修改相同记录。
3. 学习任务覆盖听、说、读、写，并支持语法和词汇等支撑练习；具体比例依用户基础和考试要求调整。语音交互、音频材料处理以及人工录入练习结果的首版范围仍需细化。
4. 保存每次练习的实际结果、错误点与来源；自动形成摘要，后续会话能够检索。AI 对能力等级的推断进入待确认状态。
5. 分开展示“已完成多少任务”“各项练习表现”“目标等级”“有证据支持的水平判断”“正式考试结果”。任务完成率不能直接换算为 B1/B2，通过用户确认的 AI 判断也不能显示为官方考试认证。
6. AI 可以结合结果建议复习或调整计划，实际新增任务、改期或改变阶段安排仍需用户确认；自动积累摘要不自动调整学习计划。

考试参考只用于指导设计，不代表用户已经选定考试。以 DELE 为例，官方 B1、B2 结构均含阅读、听力、书面表达与互动、口头表达与互动，因此不能用纯文字聊天或词汇量覆盖全部备考能力：[DELE B1](https://examenes.cervantes.es/es/dele/examenes/b1)、[DELE B2](https://examenes.cervantes.es/es/dele/examenes/b2)。等级含义参考欧洲委员会的 [CEFR 总体描述](https://www.coe.int/en/web/common-european-framework-reference-languages/table-1-cefr-3.3-common-reference-levels-global-scale)。

首版端到端验收：配置西班牙语老师 → 导入并分配资料/Skill → 记录真实起点与时间限制 → AI 提出计划 → 确认后生成任务与排期 → 完成一次学习并保存结果 → 重启后检索历史摘要和相关记忆 → AI 提出有依据的下一步建议，确认后修改计划。验收产品流程可用，不以用户已经通过考试作为软件交付条件。

### 已确认的 AI 辅助与学习需求

- AI 执行方式：采用“先展示、确认后执行”。AI 拟创建或修改目标、项目、计划、任务及排期等业务数据时，先展示具体变更，经用户确认后再保存；不能仅因用户同意总体方案就自动写入后续所有变更。只读查询和聊天中的解释、教学不属于业务数据写入。
- 手动编辑：用户通过 LifeOS 表单、列表、日历等界面直接编辑计划、进程和内容，不必通过 AI；AI 也能协助修改同一份业务数据。用户无需跳转 Obsidian 修改。
- 角色定位：用户希望配置有针对性的助手，首版以“西班牙语备考老师”完成持续的问答式学习；底层能力支持后续替换角色和扩展其他人生领域。
- 针对性资料：用户可以上传学习资料，供助手结合资料开展讲解、提问及学习辅助；文件类型、资料归属和检索方式待讨论。
- Skill 扩展：同时支持教学方法/指令流程类 Skill，以及调用工具完成实际操作的能力类 Skill。来源包括通过聊天共同制作，以及从网上导入第三方 Skill；具体兼容格式、制作入口、代码执行方式和启用范围待细化。
- 核心职责：查看用户目标、查看任务进度，将“学习西班牙语”等较大事项拆解成足够具体、可以实际执行的最小学习行动，配合问答帮助用户学习。
- 规划与教学的关系：助手既协助制定和调整计划，也辅助实际学习；具体任务粒度、完成标准，以及学习对话如何反馈到进度与长期记忆，后续细化。
- 长期记忆：必须能够跨会话保存和检索，结合 Obsidian 中的资料持续积累、整理和更新知识；参考 Andrej Karpathy 的 LLM Wiki 思路。不能把浏览器临时聊天历史当作长期记忆实现。
- 记忆积累权限：学习记录、对话摘要、资料摘要可以自动积累；AI 修改目标、项目、计划、任务与排期仍需用户确认；“已掌握某项能力”等 AI 判断先保存为待确认结论，不能自动转成已确认事实。

### Obsidian 与持续积累的知识库（设计方向）

已确认的是本地 Vault 保存数据、长期记忆检索，以及以 LifeOS 前端为主要编辑入口的需求。下述文件组织与具体机制为架构建议，需在详细设计中完善后定稿，不代表已完成实现或已验证本机接入。

#### 接入与数据归属

- 建议将 Vault 内指定的 LifeOS 目录作为业务内容与知识的持久保存位置。设置页保存用户选择的仓库路径；普通文件读写通过统一的本地文件适配层完成，CLI 作为可选的打开、定位或 Obsidian 专有能力适配器。
- Obsidian 官方说明 Vault 是本地目录，笔记是 Markdown 文件，可由其他编辑器修改，外部变化会被 Obsidian 识别：[数据存储说明](https://help.obsidian.md/Files+and+folders/How+Obsidian+stores+data)。
- 官方 CLI 要求 Obsidian 应用运行，未运行时首条命令可能启动应用。因此不建议把全部后台读写强制绑定到 CLI。实施前需核对安装版本、CLI 注册状态以及目标仓库，不能依赖当前活动笔记或当前活动仓库作为隐式目标：[CLI 说明](https://help.obsidian.md/cli)。
- 每类数据只确定一份权威记录。不能让数据库、Markdown 和浏览器本地存储各维护一份可独立修改的同类数据。
- 根据“主要在 LifeOS 编辑”的已确认约束，建议结构化业务记录（目标、项目、任务、排期、配置、会话及操作状态）使用 Vault 内的 SQLite 主数据库；原始附件按文件保存，知识笔记与长期记忆正文采用 Markdown。SQLite 适用于桌面应用的本地数据文件：[官方适用场景](https://www.sqlite.org/whentouse.html)。数据库驱动、最终目录及表结构在详细方案中确定。
- SQLite 主数据库保存业务的权威记录，必须备份，不能当成可删除的缓存。全文/向量检索索引属于可重建的衍生数据，应与权威记录明确区分；索引重建不能删除任务状态、会话或用户确认结果。
- 知识与记忆 Markdown 的正文作为对应内容的权威文件，由 LifeOS 的编辑界面和统一写入服务维护。数据库中的检索副本必须标记为派生内容。若将业务数据输出成可读笔记，该笔记应标明为展示快照，不再解析回业务数据库作为另一条独立写入通道。
- 用户不必学习上述存储格式。建立目标、调整任务、管理资料、修正记忆、安装 Skill 和备份恢复均应在 LifeOS 内提供完整入口。
- API Key 的保存需要单列设计：建议使用操作系统凭据存储，作为“内容数据存于 Vault”的明确例外；此例外待用户确认，不把密钥写入可检索笔记或默认知识上下文。
- 使用用户自备的远程模型 API 时，按实际问题发送选定范围内的必要内容；本地保存与远程推理是不同环节，接入方案需写清检索和发送范围。

#### 原始内容、长期记忆与知识整理

Karpathy 的作者 Gist 目录将 LLM Wiki 介绍为持续维护个人知识库的思路，强调知识应积累而非每次从原始资料重新拼装。参考：[作者目录中的 LLM Wiki](https://gist.github.com/karpathy?direction=desc&sort=updated)、[原始文稿链接](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。以下为针对 LifeOS 的设计建议，不作为某个第三方项目的已实现功能。

| 内容层 | 保存什么 | 作用 |
| --- | --- | --- |
| 原始资料与会话 | 上传资料、用户笔记、聊天记录、实际学习记录 | 提供可追溯依据；AI 整理时不覆盖原文 |
| 个人长期记忆 | 用户明确表达的偏好、已确认的目标与决定、学习进展、需要复习的内容 | 支持后续会话继续协助；区分用户陈述、实测记录与 AI 推测 |
| 持续整理的知识页 | 主题说明、资料摘要、概念关系、学习总结与索引页 | 把多次学习和阅读沉淀为可复用、互有关联的知识 |
| 检索索引与处理状态 | 文件内容哈希、处理版本、检索索引、待处理工作状态 | 增量处理、搜索加速、去重和中断恢复；索引不代替内容本身 |

处理链路：新增资料或产生学习/对话记录 → 保存原始内容 → 分类生成记录、摘要或候选判断 → 记录与摘要自动保存，能力判断进入待确认状态，业务修改进入变更提案 → 更新来源引用与检索索引 → 下次对话按角色权限和内容状态检索。

- 持久保存不等于模型每次都能读取全部历史。每轮先检索当前角色获准使用的内容，再将有限的相关记录及来源提供给模型；允许用户打开来源核对。
- 记忆与知识更新记录来源、时间、所属角色/共享范围和状态。AI 的推测不能默认为已确认事实；新旧资料冲突时保留差异并标出待确认点，不能静默把旧结论改成新事实。
- 自动积累与人工确认边界已确定，详见下节。具体分段时机、处理频率及模型调用成本控制在详细设计中定义；不能用知识整理流程绕过业务修改确认。
- 生成的新知识和摘要必须延续来源的使用范围，不能通过共享摘要或跨笔记链接把未分配资料带给其他角色；跨范围共享需要用户配置。
- 用原始来源的内容版本记录已处理状态，避免一次生成的摘要又被当作全新的原始来源无限触发整理；客户端关闭期间不执行，错过的定时整理由用户手动启动。
- 用户需能查看、纠正和删除记忆；删除或明确要求忘记的内容要同步失效检索索引，且不能在后续重复处理旧对话时自动恢复。具体保留记录和恢复策略在详细设计中定义。

#### 已确认的自动积累与人工确认规则

| 操作或内容 | 系统行为 | 是否等待确认 |
| --- | --- | --- |
| 实际发生的学习记录 | 保存练习内容、时间、回答及可核实结果，引用原始会话或练习记录 | 自动保存 |
| 对话摘要、资料摘要 | 提炼并保存内容，标记为 AI 生成摘要并保留来源；用户可在 LifeOS 查看、纠正和删除 | 自动保存 |
| 能力掌握、水平提升等推断 | 保存为待确认结论，展示判断及依据；用户可确认、修改后确认或拒绝 | 确认后才作为已确认结论使用 |
| AI 创建、修改、删除目标/项目/计划/任务，标记任务完成或调整排期 | 展示具体对象与变更内容，绑定当前记录版本；确认后通过业务服务执行 | 必须确认 |
| 用户在 LifeOS 界面直接编辑或勾选任务 | 按用户明确的界面操作保存；自动同步相关页面 | 不额外增加 AI 确认步骤 |

以上允许自动积累的是来源可追溯的记录与摘要，不授予 AI 自动认定用户能力、修改用户目标、覆盖手动纠正内容或改动业务状态的权限。自动摘要生成成功表示内容已保存，不表示其中所有陈述都经过用户确认。

实现约定：

1. 内容类型与确认状态分开保存。至少能区分学习记录、生成摘要、能力判断，并保留来源、角色/共享范围、内容版本及生成时间；能力判断使用独立的待确认、已确认、已拒绝状态，不把自动摘要统一标记为“已确认事实”。
2. 检索结果携带类型、状态与来源。待确认判断不能用于把任务自动标记完成、更新能力等级或自动跳过学习内容；如在对话中提及，须明确为待确认判断。摘要不得把来源中的待确认判断改写成已确认结论。
3. 在 LifeOS 提供待确认结论入口，展示判断及依据并支持确认、编辑、拒绝。用户确认仅对具体判断及其版本生效；拒绝后，相同证据不得重新生成同一条待确认请求。新证据支持的不同判断需明确说明变化。
4. 摘要生成与业务写入走不同路径。学习摘要可以记录“本次练习答对 8/10 题”，但不能据此自动保存“掌握该知识点”或完成关联任务。任务等业务变更仍通过此前约定的提案确认机制执行。
5. 自动整理仅在 LifeOS 运行时执行。已持久保存但因退出而未完成的整理保留状态，下次启动提供手动继续入口，不自动补跑；不因摘要失败丢失原始学习记录。具体运行中重试规则在详细设计中定义。
6. 按来源标识、来源版本和处理类型去重；对同一原始内容重复处理不得重复创建记录。用户纠正、拒绝或删除后，后续自动整理不得静默撤销该操作。

对应验收场景：

- 完成一段学习后，无需逐条批准即可保存学习记录与摘要，重启后仍可检索；关联目标、任务和排期不因摘要生成而改变。
- AI 生成“已掌握某项能力”时，显示为待确认；确认前，下一次对话与进度展示均不得把它当作已确认能力。
- 设置“目标 B2”后，当前水平仍保持未知或已有测评记录，不能因此生成“用户已达 B2”的记忆；AI 评估、用户确认与正式考试成绩分别标识。
- 用户拒绝该判断后，同一证据的重复整理不会恢复该判断或再次弹出相同请求。
- 自动摘要含有待确认判断时保留其状态与来源；另一个未获配这些内容的角色无法通过检索摘要间接读取。
- AI 提议修改任务时，取消提案不改数据，重复确认不重复执行；确认前发生手动编辑时提示变更冲突。
- 整理过程被退出中断后，原始记录仍在；重新打开需用户手动继续，继续处理不会重复保存同一份摘要。

#### 文件编辑、恢复与后续设备

- 第一版以 LifeOS 统一写入为正常流程，不开发任意 Obsidian 任务格式与 LifeOS 业务记录的双向同步。仍需识别应用管理的知识文件被外部编辑、移动或删除：核对版本并提示重新读取或处理冲突，不能静默覆盖。具体异常处理在详细方案中定义。
- 多文件变更需要变更清单、恢复记录与失败处理；不能把逐个写文件当成天然具备事务性。任务与项目等关联采用稳定 ID，不仅依靠文件名。
- Vault 备份应包含原始记录、资料附件、配置与必要的恢复记录；检索索引允许重建。未来手机同步时需区分内容文件、设备配置和可重建缓存，不能直接并发同步正在写入的数据库文件作为默认方案。
- 第一阶段增加“在 LifeOS 选择 Vault、保存业务记录与知识笔记、重启恢复”的验收，知识笔记可在 Obsidian 查看。完整业务验收必须可以只通过 LifeOS 界面完成；不以手动编辑 Obsidian 文件补足缺失的前端功能。后续验证覆盖索引重建、角色隔离、记忆纠错及中断恢复。

### Skill 设置入口与实现差距

- 用户要求衔接现有设置页面中的技能管理功能，方案以现有“设置 → Agent → 技能”入口为基础完善。
- 代码核对：`index.html` 的 `tabSkills()`、`refreshSkillsList()` 和 `bindSkillEvents()` 已有技能列表及启用/停用交互，页面明确标注内置技能是演示实现；当前尚无完整的自定义 Skill 制作和第三方安装流程。
- 后端核对：`server/routes/skills.js` 只有列表、启用/停用、更新配置接口；`server/services/skills.js` 仅用固定分支处理四项内置技能，尚无通用的第三方 Skill 加载及执行机制。不能把已有界面入口视为安装能力已经完成。
- 详细方案需补齐：Skill 的制作/导入、元数据与版本、配置、角色绑定、启用/停用、卸载及执行结果记录；明确指令类与工具类 Skill 各自如何加载，以及支持哪些第三方包格式和运行依赖。
- 已确认采用按需共享：资料和已安装 Skill 统一管理，由用户为每个 Agent 手动配置使用范围；安装或上传不代表所有 Agent 自动获得访问权。同一资料或 Skill 可以分配给多个 Agent，未配置的 Agent 不得使用。
- 实施约束：角色绑定必须由后端在检索资料、装载 Skill 指令、提供工具及实际执行时校验，不能仅靠前端隐藏选项或角色提示词限制。解绑/停用后不得继续加载或调用；已产生的聊天内容如何保留，在记忆规则中另行定义。

本节目前是实施框架，不代表需求和技术选型已经定稿。最终交接前必须把各阶段细化到具体文件、数据结构、接口、依赖和可执行的验证命令；本轮不启动业务开发。

#### Harness 子 agent 的创建方式

已于 2026-09-20 核对官方文档。当前官方提供子 agent 委派工具；工具名取决于配置。以下是开发运行环境的组合片段，应用前由主 agent 检查已安装版本和已加载插件，避免重复注册；这不是 LifeOS 的应用配置。

```yaml
- name: '@deepseek-ai/dsh-subagent'
- name: '@deepseek-ai/dsh-subagent-spawn-in-process'
- name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: subagent
    backgroundMode: continuable
    maxDepth: 1
- name: '@deepseek-ai/dsh-tool-subagent-control'
```

官方依据：[委派工具配置](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/tool-subagent/README.md)、[spawn 子 agent](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/subagent-spawn-in-process/README.md)、[子 agent 控制工具](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/subagent/tool-subagent-control/README.md)。

- 主 agent 使用运行环境实际暴露的委派工具，以完整任务说明创建子 agent；可独立推进的任务使用后台执行，并记录返回的子 agent 标识。
- `spawn` 子 agent 以新的对话开始，派单必须自包含，不能假设它读过父对话。共享运行服务也不代表具有独立文件副本；文件写入范围必须明确分配。
- 在已启用的持续子 agent 模式下，通过实际暴露的消息/状态控制工具跟进和续派任务。主 agent 必须接收最终报告、检查文件并验证结果，创建成功不等于工作完成。
- 具体工具参数以当前工具声明为准。执行前先验证委派与结果回收；能力不可用时将同样的任务顺序执行，并记录原因，不得把未运行的任务写成已完成。
- 默认由主 agent 统一派单，子 agent 不继续递归创建其他实现者。子 agent 的模型默认沿用用户配置，不擅自切换付费提供商。

1. 主 agent 派单前明确该任务允许修改的文件和依赖的接口版本；接口还在变化时，先完成约定再并行实现。
2. 公共入口、数据库迁移顺序、依赖清单、锁文件、共享类型和 README 的进度记录由主 agent 或其指定的单一负责人修改。子 agent 提出变更请求后，由负责人统一整合。

## 当前轮任务

### 第 3 轮：领域项目保持独立选中状态

状态：方案已确认并写入 README，尚未修改页面代码。

#### 用户期望

- 点击哪个项目，就只高亮该项目。
- 其他领域中的项目不得因为共用同一个详情页面而一起高亮或一起熄灭。
- 项目选中状态与领域展开状态互不影响。
- 点击另一个项目时，高亮从原项目移动到新项目；每次最多只有一个项目处于选中状态。

#### 问题原因

当前侧栏项目通过两类页面路由打开详情：

- “AI 智能体开发”进入 `agent` 页面。
- 其他多数项目进入通用的 `simple` 页面。

现有 `render()` 使用 `data-page === current` 判断所有导航项是否高亮。由于多个不同项目都使用 `data-page="simple"`，进入其中任意一个项目时，所有指向 `simple` 的项目都会被视为当前项目。这是“多个项目同时亮起或熄灭”的根本原因。

页面路由只能表示“打开哪种页面”，不能作为项目的唯一选中标识。

#### 状态设计

导航需要明确区分三类状态：

| 状态 | 用途 | 建议标识 |
| --- | --- | --- |
| 当前页面 | 决定渲染领域页或详情页 | `current` / `data-page` |
| 当前项目 | 决定唯一高亮的项目 | `selectedProjectId` / `data-project` |
| 展开的领域 | 决定哪些项目列表可见 | `openAreas` / `data-sub` |

项目必须使用自己的唯一 ID 判断选中状态，例如 `p-lifeos`、`p-course`，不能再通过 `simple` 或项目名称判断。

#### 实施方案

1. 新增独立的 `selectedProjectId` 状态，保存用户最后点击的项目 ID。
2. 项目点击时同时更新 `selectedProjectId` 和详情页所需的 `pendingProject`。
3. 将 `render()` 中统一处理 `[data-page]` 的高亮逻辑拆分为 `updateNavState()`。

```js
const viewingProject = current === 'simple' || current === 'agent';
```

### 第 1 轮：侧栏展开箭头位置与旋转修复

状态：已明确需求，待实现 agent 修改，尚未验收。

用户反馈：「事业发展」导航的展开箭头在动画后出现在按钮上方。预期箭头始终位于对应按钮内部右侧，与文字垂直居中。

#### 原因与公共 UI 约定

代码中 `.nav-item span,.nav-parent span{flex:1}` 同时作用于文字和 `.chev` 箭头容器。箭头容器被拉宽，旋转整个容器时，内部图标绕偏离自身中心的原点移动。这与截图中的偏移一致，需在浏览器中验证修复。

- 导航统一分成左侧固定图标、中间弹性文字、右侧固定箭头三个部分；只有文字占用剩余空间。
- 箭头容器固定为 14×14px，禁止 flex 拉伸和收缩，内部 SVG 居中并显式设置为 14×14px、块级显示。
- 只旋转箭头 SVG，以自身中心为旋转原点；收起朝右、展开朝下，保留约 180ms 的过渡，并遵守现有减少动画设置。
- 不使用负边距、绝对定位偏移或额外位移补偿掩盖布局问题。

- 规划 agent 维护 `README.md` 中的要求与验收记录。
